# Research: Organization Settings and Module Controls End to End

**Feature**: `specs/018-org-settings-modules/spec.md` | **Date**: 2026-11-19

All Technical Context entries were resolved from the repository itself (package manifests, schema, guards, test fixtures and CI workflow), so no `NEEDS CLARIFICATION` marker remained to research. The decisions below settle the *how* for the ambiguities the spec leaves to design, grounded in the patterns already used by Features 001–017.

---

## 1. Version and optimistic locking

- **Decision**: Add `version Int @default(1)` to `Organization` (model at `database/prisma/schema.prisma:152-194`), mirroring `Membership.version` (`schema.prisma:203`) and the `20261116000001_membership_name_version` migration. `organization_modules` also carries `version Int @default(1)`. Both PUT endpoints accept a `version` in the body and perform a conditional `updateMany` on `(id, version)` (or `(organization_id, module_key, version)`), incrementing version; zero matching rows → 409 `STALE_VERSION`. The response returns the new version so the client can continue editing.
- **Rationale**: Matches the established optimistic-locking pattern, avoids a full ownership/status check, and satisfies FR-006 and Clarification Q2 with one mechanism for settings and toggles.
- **Alternatives considered**: (a) last-write-wins — rejected (FR-006 forbids it); (b) a separate revision table — rejected as extra schema with no benefit over the column pattern already used nine times; (c) returning the version in a header — rejected because the API contract uses JSON bodies throughout.

## 2. Currency lock and its race with document creation

- **Decision**: Add a migration that (a) creates `organization_modules` with RLS enabled and no policies, (b) backfills all existing organizations with the five switchable modules enabled, and (c) installs a schema-pinned `BEFORE UPDATE` trigger on `organizations` that raises an exception when `currency_code` changes while any `sales_orders`, `purchase_orders` or `invoices` row exists for that organization, in any status. Application-level lock: `TransactionService.runInTransaction` acquires a `SELECT … FOR UPDATE` row lock on the `organizations` row at the start of a settings currency change and at the start of purchase-order, sales-order, invoice and active-reservation creation. The currency existence check runs under that lock; the trigger is the backstop for any path that bypasses the service.
- **Rationale**: A row lock on the single organization row is simple, uses the existing transaction service, and serializes exactly the two operations the spec requires (FR-010/FR-011). The trigger protects against direct SQL and any future creation path that forgets the service call. `pg_advisory_xact_lock` was considered but adds a key-derivation scheme without improving correctness.
- **Alternatives considered**: (a) application check with no lock — rejected (fails the race test); (b) advisory lock only — rejected because the org row lock is already available and covers the same serialization; (c) immutability revoke of the currency column — rejected because name and terms must still be editable.
- **Tradeoff**: The org row lock briefly serializes document creation per organization; acceptable for the v1 pilot and bounded by the short transaction. Recorded here rather than in Complexity Tracking because it is a performance characteristic, not a constitution violation.

## 3. Module availability, dependencies and open-document counts

- **Decision**: `organization_modules` has composite primary key `(organization_id, module_key)`, columns `enabled Boolean`, `version Int`, `created_at`, `updated_at`, and an FK on `organization_id` to `organizations(id)`. Module keys are `inventory`, `purchasing`, `sales`, `invoicing`, `reports` (switchable) and `contacts`, `products`, `settings`, `audit` (always on; no rows required). Dependencies are a small in-code map (`sales→inventory`, `purchasing→inventory`, `invoicing→sales`) owned by the Organizations module; the toggle service checks both directions inside the same locked transaction. In-use counts are computed with parameterized `count` queries over the status sets in FR-017, plus active `StockReservation` rows for inventory. Refusals use the `details[]` array of the shared error envelope: one detail per module/count so the interface can show "names and counts" without parsing a message (resolves the Deferred item from `/speckit.clarify`).
- **Rationale**: A composite primary key enforces one row per module per organization; the in-code dependency map is small, immutable and testable; `details[]` is the existing contractual place for structured field/check detail.
- **Alternatives considered**: (a) storing dependencies in a table — rejected as extra schema for three fixed rules; (b) free-text refusal messages — rejected because FR-037 requires counts the UI can render; (c) treating always-on modules as rows that can never be disabled — rejected because it would create rows the invariants do not require and invite accidental toggles.

## 4. Module toggle race with document creation

- **Decision**: The toggle transaction takes the same `organizations` row lock as document creation, then re-reads module state and open-document counts. Document-creation services additionally call a shared `assertModuleEnabled(tx, organizationId, module)` after acquiring the lock, so a guard decision made before the lock cannot let a document through after a concurrent toggle. A `Promise.all` race test (pattern: `backend/test/integration/payments-concurrency.spec.ts`) asserts exactly one success and checks the resulting DB state.
- **Rationale**: Satisfies FR-018 and the "exactly one outcome" acceptance scenarios without relying on request-time guard state alone.
- **Alternatives considered**: (a) relying only on the request guard — rejected (race window); (b) disabling writes during a toggle via a global flag — rejected (unscoped, and would affect other tenants).

## 5. One shared module guard, read once per request

- **Decision**: Replace the three identical pass-through guards with one `ModuleGuard` in `backend/src/common/guards/`, backed by a request-scoped `ModuleStateService` that loads the organization's module rows once and caches them on the existing `RequestContext` (`AsyncLocalStorage`, `backend/src/common/logging/request-context.ts`) for the lifetime of the request. A generic `@RequireModule('inventory'|…)` decorator with metadata key `nexuserp:module` declares the requirement; the existing `@PurchasingModule()`, `@SalesModule()` and `@InvoicingModule()` decorators become thin aliases so the existing declaration specs keep their shape. The guard denies by default when metadata is absent, and returns 403 `MODULE_DISABLED` with the module key in `details` when the row is disabled. Controllers of Inventory and Reports gain the same guard and every handler gains `@RequireModule('inventory')` / `@RequireModule('reports')`, reads included.
- **Rationale**: One implementation of the rule, one cache read per request, and a single structural test can assert every endpoint of every switchable module declares the requirement (FR-020/021/022).
- **Alternatives considered**: (a) keeping three separate guards — rejected (FR-020 requires one shared guard and there would be no Inventory/Reports coverage); (b) a global guard with no declaration — rejected (default-deny would break unrelated endpoints); (c) caching module state in a module-level singleton — rejected (stale across tenants and toggles).

## 6. Error codes and audit actions

- **Decision**: Add `CURRENCY_LOCKED`, `MODULE_DEPENDENCY` and `MODULE_IN_USE` to all four maps in `shared/src/errors/index.ts` (`ERROR_CODES`, `EMITTABLE_ERROR_CODES`, `ERROR_CODE_STATUS` → 409, `DEFAULT_ERROR_MESSAGES` with user-safe messages). Add `organizations.updated` and `organizations.module_toggled` to `AUDIT_ACTIONS` in `shared/src/audit/index.ts`; `AuditService.record()` already joins the ambient transaction, so both changes call it inside `TransactionService.runInTransaction`. Because the dashboard activity map asserts coverage of every backend action code, add both labels to `frontend/src/features/overview/activity-labels.ts` and to the en/ar dashboard locales.
- **Rationale**: The shared catalogue is the single source of truth for codes, statuses and messages; adding codes there keeps the contract, client and tests in agreement. Audit codes must be added or the existing fail-safe test breaks (and the feature requires the entries anyway).
- **Alternatives considered**: (a) reusing `CONFLICT` — rejected because the interface must branch on the specific refusal; (b) reusing an existing audit code — rejected because the action vocabulary is contractual and reused codes would mislabel history.

## 7. Registration and session payload

- **Decision**: Extend `registerSchema` (`backend/src/modules/auth/dto/register.dto.ts`) with optional `organizationName` (trim, 1–100) and optional `currencyCode` (one of the eight supported codes, default `USD`), replacing the current 2–128 name bound. The existing `tx.organization.create` at `auth.service.ts:51-53` gains the supplied name/currency and is followed by `tx.organizationModule.createMany` for the five switchable modules in the same transaction. The response contract stays unchanged. Extend `/auth/me` (`auth.service.ts:288-301,393-396`) with `enabledModules`, `organization.currencyCode` (already present) and `organization.defaultPaymentTermsDays`; `loadSignedInSession()` in `frontend/src/services/auth-session.ts` hydrates them into `SessionOrganization`. The Organization page invalidates the session query (`bootstrapSession(true)`) after a successful save or toggle so the top bar, currency and module state refresh in place (Clarification Q3).
- **Rationale**: Registration is the only place module rows are created for new tenants; the session payload is already the single source of currency and module data for the shell, so extending it adds no new request (FR-027).
- **Alternatives considered**: (a) a separate `/auth/me/modules` call — rejected (FR-027 says no extra calls); (b) deriving modules from permissions — rejected (FR-002 separates workspace availability from member authority).

## 8. Interface adaptation without touching the static navigation list

- **Decision**: `frontend/src/components/shell/sidebar.tsx` keeps rendering `NAVIGATION` verbatim but marks entries whose module key is disabled as unavailable with the existing `shell.sidebar.turnedOff` label ("Turned off in Settings") by reading `session.organization.enabledModules`. `AppShell` already redirects disabled paths to `/settings/organization` with that notice — replace its `sampleCatalogService.listModules()` query with the session-derived modules and extend `gatedModule` to include `reports`. Overview widgets/quick actions and Reports sections filter on the same set (Reports hides each section whose source module is disabled, per Clarification Q4). `frontend/src/components/shell/__tests__/navigation-master-file.spec.ts` remains the guard that the static list and design-system table are untouched.
- **Rationale**: Runtime state is layered on a static list, which is exactly FR-042, and reuses the label and redirect the shell already has.
- **Alternatives considered**: (a) filtering `NAVIGATION` itself — rejected by FR-042 and the master-file guard; (b) a separate module-configuration service — rejected because that is the sample-data path being removed.

## 9. Sample-data removal and its guard

- **Decision**: Delete `frontend/src/services/sample-catalog-service.ts`, `frontend/src/config/real-modules.ts` and `frontend/src/components/ui/sample-data-banner.tsx`; rewrite the production consumers (`app-shell.tsx`, `sidebar.tsx`, `command-palette.tsx`, `document-trail.tsx`, `administration/use-administration.ts`, `organization-page.tsx`, `audit-log-page.tsx`) to use real services. The development gallery keeps its own fixtures under `frontend/src/dev/gallery/**`. Add `frontend/scripts/check-no-sample-imports.ts`, modelled on `check-no-raw-design-values.ts`, exporting a pure matcher with an explicit allowlist limited to `src/dev/gallery/**` and `__tests__/**`; add `frontend/scripts/__tests__/no-sample-imports.spec.ts` including a deliberately failing fixture (demonstrated once, then reverted), and wire the script into the `frontend` `build` chain and a root guard script.
- **Rationale**: A repository-wide static guard is the only way to prove FR-045/SC-008; the existing partial guard (`src/components/__tests__/no-direct-sample-imports.spec.ts`) covers only one folder and one pattern.
- **Alternatives considered**: (a) relying on code review — rejected by FR-047; (b) a runtime check — rejected (cannot prove absence of imports).

## 10. Verification, invariants and contract

- **Decision**: Add three numbered checks at the end of `scripts/verify-db-invariants.mjs` (after check 23, before the summary) for module-row coverage, dependency consistency and the presence of the currency-lock trigger (pattern: check 17's `pg_proc` lookup); extend the header's invariant list. Add integration specs in `backend/test/integration/` following `payments-concurrency.spec.ts` (races), `invoicing-isolation.spec.ts` (two-org isolation/permission matrix), and `purchasing-endpoint-declarations.spec.ts` (structural declaration assertions extended to all five switchable modules). Build the API, run `npm run openapi:generate`, then `npm run openapi:diff`. Prove public row counts unchanged with `scripts/snapshot-public-counts.mjs` around the isolated-schema run.
- **Rationale**: Reuses proven fixtures and guards; one script verifies both schemas because it reads `current_schema()`.
- **Alternatives considered**: (a) a separate invariants script for each schema — rejected (the existing dual-schema design already works); (b) adding the contract by hand — rejected (drift check would fail).
