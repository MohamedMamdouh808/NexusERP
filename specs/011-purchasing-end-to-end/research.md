# Phase 0 Research: Purchasing end to end — real purchase orders and goods receipts

**Feature**: 011-purchasing-end-to-end · **Date**: 2026-11-12 · **Updated**: 2026-11-13 (clarification session) · **Spec**: [spec.md](./spec.md)

Every unknown in the Technical Context was resolved against the repository before this file was written: the Inventory adjustment/idempotency pattern, the Products/Contacts version and audit patterns, the `PRODUCTS_USAGE_HOOK` seam, the document-sequence numbering, the append-only audit migration, the OpenAPI drift tool and the frontend service seam. No external research was needed.

**2026-11-13 amendment.** The specification was clarified in a second session, and five answers changed decisions that D1, D3 and D9 had already taken. Those three decisions are amended in place below, and D12–D18 record the new ones: the receipt-level list row, the order progress summary, the unit-of-measure snapshot, the shared module gate, the sequence provisioning, the receive-dialog behaviour and the receipt permission.

## D1 — Purchase-order and goods-receipt numbering

- **Decision**: Allocate both numbers inside the business transaction from the existing `document_sequences` table, using the same advisory-lock pattern as Inventory adjustments: `pg_advisory_xact_lock(hashtext('<organizationId>:purchase_order'))` and `...:goods_receipt`, then find-or-create the sequence row, increment it, and format `PO-` / `GR-` followed by six digits. A rolled-back transaction returns the number because the sequence row's increment rolls back with it. The sequence row is created on first use rather than backfilled, and the table gains a unique constraint on `(organization_id, name)` so two concurrent first-uses cannot create two rows (D16).
- **Rationale**: The sequence table is already the product's numbering mechanism; the advisory lock serializes two allocations without taking a row lock on `organizations` (which would collide with the key-share locks the composite FKs take). Six digits matches the spec and the existing `PO-000001` / `GR-000001` examples.
- **Alternatives considered**: PostgreSQL `SEQUENCE` objects (a new mechanism, and gaps are harder to reason about per organization — rejected); counting existing rows (races and reuses numbers after deletes — rejected); allocating outside the transaction (a rollback leaves a gap the user cannot explain — rejected).

## D2 — Receipt locking order and the receipt-versus-cancel race

- **Decision**: A receipt transaction locks the purchase-order row `FOR UPDATE`, then its lines in ascending line id `FOR UPDATE`, then posts stock movements in ascending product id. It does not take an order version from the client. Confirm, cancel and update take the same order row lock first. Cancel checks for any receipt after taking the lock; a receipt checks the order status and outstanding quantities after taking the lock. The two outcomes are therefore ordered by the database: either the receipt commits first and the cancel sees a receipt (`ORDER_HAS_RECEIPTS`), or the cancel commits first and the receipt sees a non-receivable status (`INVALID_STATE_TRANSITION`).
- **Rationale**: The order row is the single serialization point for every write to one order, so two receipts on the same line cannot each read the same outstanding quantity. Ordering the line locks and then the balance locks prevents deadlock when different orders share products: the last lock class is always acquired by ascending product id.
- **Alternatives considered**: relying only on the `quantity_received <= quantity_ordered` check (correct for over-receipt but produces an unhelpful constraint error and does not order the cancel race — rejected); a separate `SELECT ... FOR UPDATE` on every balance before validation (extra locks and still needs the product order — rejected); versioning the receipt request (the spec explicitly says receipts do not carry the order version — rejected).

## D3 — Idempotent receipt posting

- **Decision**: Reuse `IdempotencyService.runOnce` with endpoint `/purchase-orders/:id/receipts`, the organization from the session, and the request body exactly as received. The claim is written inside the receipt transaction; the business change runs; the response `{ receipt: { id, number }, order: { number, status } }` is stored on the claim. The same key and same body replays the stored result. The same key with a different body returns 422 `IDEMPOTENCY_KEY_REUSED`. The frontend generates the key when the Receive goods dialog opens and reuses it for every retry of that attempt; a new key is generated only when the previous attempt ended in a definite answer, and an attempt whose outcome was unknown keeps its key (D17).
- **Rationale**: This is the existing, tested platform behaviour; the receipt adds no second idempotency mechanism. A rollback removes the claim because the claim is in the same transaction, so a corrected retry is allowed.
- **Alternatives considered**: a unique constraint on `goods_receipts (organization_id, purchase_order_id, ...)` (there is no natural one-time business key — rejected); an in-memory key map (lost on restart, not shared — rejected); storing the key after the receipt (a crash could post twice — rejected).

## D4 — Usage guards without a module cycle

- **Decision**: Add a dependency-light `PurchasingUsageModule` that reads only Purchasing tables through `PrismaService` and exposes three explicit answers: open product usage, open supplier usage and open warehouse usage. Each returns the oldest blocking order number. `InventoryModule` imports this module so its products provider combines reserved stock with open purchase orders and its warehouse deactivation consults the warehouse answer. `ContactsModule` imports it and provides a `CONTACTS_USAGE_HOOK` implementation that asks it. `PurchasingModule` imports Products/Contacts/Inventory for forward validation, but none of those imports PurchasingModule.
- **Rationale**: The existing seams are one-answer hooks. Purchasing cannot replace the Inventory-backed products provider without losing the reserved-stock answer, and Inventory cannot import PurchasingModule without a cycle because Purchasing already needs InventoryService. A tiny reverse-answer module that owns only the purchasing queries breaks the cycle while keeping every table read inside its owning module.
- **Alternatives considered**: `forwardRef` (the constitution prohibits circular module dependencies — rejected); moving purchasing usage queries into Products/Contacts/Inventory (cross-module table reads — rejected); a global event bus (new infrastructure and eventual consistency for a synchronous archive check — rejected).

## D5 — Forward validation and locks for supplier/product/warehouse

- **Decision**: Create and update lock the supplier, then the warehouse, then the products in ascending product id, through methods owned by ContactsService, InventoryService and ProductsService (`assertSupplierSelectableForOrder`, `assertActiveWarehouseForOrder`, `assertSelectableForOrder`). Each method takes the transaction client, uses `SELECT ... FOR SHARE`, and returns the summary Purchasing needs. Lists and details use non-locking bulk summary reads; list search by supplier or product uses owning-service id-search methods (`findMatchingSupplierIds`, `findMatchingProductIds`) rather than joining another module's table.
- **Rationale**: A plain read validation has a race: a product could be archived between the check and the order commit, leaving an open order pointing at an archived product. A shared row lock makes the archive wait; when it proceeds, its usage hook sees the committed order. The fixed lock order prevents two order writers from deadlocking on the same supplier/warehouse/product set. Owning services keep their tables private.
- **Alternatives considered**: direct Prisma queries from Purchasing (forbidden cross-module table reads — rejected); no locks, usage checks only (leaves the archive/create race — rejected); locking the whole organization row (collides with FK key-share locks — rejected).

## D6 — Exact decimals and the three rounding vectors

- **Decision**: Quantities are `NUMERIC(14,3)`, unit cost `NUMERIC(14,4)`, line/order totals `NUMERIC(14,2)`. DTO validation accepts decimal strings with at most 3/4 places and rejects extra places rather than rounding. The service uses `Prisma.Decimal` (decimal.js): `new Prisma.Decimal(quantity).mul(unitCost).toDecimalPlaces(2, Prisma.Decimal.ROUND_HALF_UP)` per line; the order total is `sum(lineTotal)` with no re-rounding. JSON responses call `toFixed(3)`, `toFixed(4)` and `toFixed(2)`.
- **Rationale**: This is the constitution's exact rule and the codebase's existing decimal vocabulary. Per-line rounding then summing is the only way the three vectors (`3.333 × 1.2345 = 4.11`, `1.000 × 0.0050 = 0.01`, `2.500 × 4.5000 = 11.25`) and the total invariant can both hold.
- **Alternatives considered**: JavaScript numbers (forbidden — rejected); summing unrounded products then rounding once (produces a different total from the lines — rejected); database-side rounding of the total (would disagree with the application's displayed sum — rejected); a database check on the line total is added as a second line of defence, not as the primary calculation.

## D7 — Receipt request shape and line matching

- **Decision**: `POST /purchase-orders/:id/receipts` takes `{ lines: [{ lineId, productId, quantity }] }`. Every entry must name a line that belongs to the order and a product that matches that line; duplicate `lineId` entries are refused. Entries with zero or blank quantities are accepted in the request but create nothing; if no entry has a positive quantity the whole receipt is refused with 400 `VALIDATION_ERROR`. Positive quantities above the line's outstanding quantity are refused with 400 `OVER_RECEIPT` naming the outstanding quantity. Only positive entries create receipt lines and movements.
- **Rationale**: The line id removes any ambiguity when an order has one line per product, and the product id makes a mismatched pair detectable. The all-zero refusal is a product rule from the spec; accepting zero rows lets the dialog submit the full line set without having to filter client-side. The service still filters, so a zero can never become a stored receipt line.
- **Alternatives considered**: product-only matching (cannot detect a line from another order cleanly — rejected); storing zero receipt lines (violates the spec's "a zero is never stored" — rejected); rejecting a request that contains zero entries (would force the client to filter and could hide a mismatch — rejected).

## D8 — The Inventory service's receipt method

- **Decision**: Add `postReceiptMovement({ organizationId, userId, warehouseId, productId, quantity, receiptId, receiptNumber })` to `InventoryService`. It joins the ambient transaction, re-checks that the warehouse is active (Inventory owns warehouses) and the quantity is positive, performs one guarded upsert (`on_hand = on_hand + quantity`, version increment, returning before/after), inserts a `stock_movements` row with `type='RECEIPT'`, `source_type='RECEIPT'`, `source_id=receiptId`, `source_number=receiptNumber`, and returns the movement id and the before/after on-hand strings. It does not read the products table (Purchasing's locked product guard has already answered that) and does not write an audit entry or open a transaction.
- **Rationale**: The spec requires every stock effect to go through Inventory and forbids Purchasing from writing Inventory tables. One method per received line keeps the balance arithmetic and the movement insert together. Returning before/after lets Purchasing write one receipt audit entry that records the stock effect without reading Inventory tables itself.
- **Alternatives considered**: a bulk method taking all lines (a reasonable alternative, but one-line calls make partial failure and per-line quantities clearer — rejected for this scope); writing movements from Purchasing (forbidden — rejected); posting movements after the receipt commits (breaks the one-transaction rule — rejected).

## D9 — Frontend service seam and invalidation

- **Decision**: Add `frontend/src/services/purchasing-client.ts` beside the real products/contacts/inventory clients. `use-purchasing.ts` switches every function to it. The order form uses `useProducts`, `useContacts` and `useWarehouses` for real pickers; a product selection copies `purchasePrice` into the editable unit cost. Confirm/cancel mutations take the current order version. Receipt quantities carry both `lineId` and `productId`. The receipt mutation invalidates `purchaseOrders`, `goodsReceipts`, `movements`, `stockBalances` and `lowStockCount`. The Purchasing page drops `SampleDataBanner`; `sample-catalog-service.ts` drops purchasing state and methods; the command palette's purchase-order search uses the real client. Sales/Invoicing/Overview keep their sample reads. The two lists render the server's summaries verbatim (D12, D13) instead of deriving a figure in the browser, and the module's labels move to the real-module convention: no `*` inside the label text, the shared `Input`/`Select` own the required marker, and a separate `…Required` message carries the validation text. The sample-isolation test that asserts the order form reads the sample service is rewritten in the same batch, because it asserts the behaviour this feature removes.
- **Rationale**: The hooks already isolate the screens from the data source, so the change is concentrated in the client and hook layer. Invalidating exactly the five caches keeps the Inventory screens correct after a receipt without a full reload. Keeping shipment sample state preserves the still-sample Sales/Invoicing modules.
- **Alternatives considered**: changing every component to call `fetch` directly (bypasses the seam and duplicates error handling — rejected); keeping the sample service as a fallback (would hide backend failures and show false data — rejected); invalidating every query (correct but wasteful — rejected in favour of the five known caches).

## D10 — Append-only receipts, invariants and contract drift

- **Decision**: Copy the audit-log mechanism: `BEFORE UPDATE` and `BEFORE DELETE` triggers on `goods_receipts` and `goods_receipt_lines` raise, and `TRUNCATE` is revoked. Extend `scripts/verify-db-invariants.mjs` to check: received never exceeds ordered; every order total equals the sum of its line totals; every line total equals `round(quantity_ordered * unit_cost, 2)`; status agrees with received quantities (DRAFT/CONFIRMED/CANCELLED all zero; PARTIALLY_RECEIVED has at least one positive and one outstanding; RECEIVED all equal); every receipt line has a matching `RECEIPT` movement whose source id/number agree; receipts/lines reject update, delete and truncate. Regenerate OpenAPI from the implemented controllers and add `docs/api-purchasing-contract.md`.
- **Rationale**: The audit migration is the proven append-only pattern, and the invariant script is already the release check for stock. Adding purchasing checks there keeps one verification entry point. Contract drift must fail when the documented endpoints and DTOs differ from the code.
- **Alternatives considered**: assertions only in integration tests (the invariant script is the release-level check — rejected); application-level immutability only (a direct SQL write would bypass it — rejected); hand-writing the OpenAPI document (drift — rejected).

## D11 — Lifecycle and error mapping

- **Decision**: Statuses are exactly `DRAFT`, `CONFIRMED`, `PARTIALLY_RECEIVED`, `RECEIVED`, `CANCELLED`. Create always starts DRAFT (empty lines allowed, total `0.00`). Update is DRAFT-only. Confirm is DRAFT-only and requires at least one line. Cancel is allowed from DRAFT, or CONFIRMED with no receipts. Invalid transitions and cancel-with-receipts return 409; stale versions return 409 `STALE_VERSION`; content failures return 400 `VALIDATION_ERROR`; over-receipt returns 400 `OVER_RECEIPT`; key reuse returns 422. The order row is fetched first so a stale version is distinguished from an invalid state.
- **Rationale**: The spec fixes this mapping. Fetching the row under the order lock and checking version before status gives the caller the most useful refusal and keeps the version pattern consistent with products/contacts/warehouses.
- **Alternatives considered**: checking status before version (a stale client would be told the state is invalid even though a reload would show a changed version — rejected); returning 409 for over-receipt (the spec fixes 400 — rejected).

## D12 — The goods-receipts list is one row per receipt

- **Decision**: The receipts endpoint returns one row per goods receipt — `GR-` number, linked order id and number, supplier name, warehouse name, received date, receiving user, line count, and, **only when every line of the receipt shares one unit of measure**, an aggregate received quantity with its unit abbreviation. The aggregate is a `SUM(quantity)` over the receipt's lines computed in PostgreSQL and returned as a decimal string; the uniformity test is `COUNT(DISTINCT unit_of_measure) = 1` over the same lines. The payload carries **no** line detail. The list's `total` counts receipts and the interface labels it as receipts. A product search matches any line (through the owning Products service's id search, D5) but still returns one row per receipt. The date range filters on the received date and a range whose end precedes its start is refused with 400 `VALIDATION_ERROR` naming the date field.
- **Rationale**: One row per receipt keeps the total meaningful ("N receipts"), gives one rendering path, and lets the list stay a single aggregate query over purchasing tables. Carrying no lines is what makes the conditional aggregate necessary: summing quantities whose units differ would be a meaningless number, so the row carries the line count instead. A single aggregate query per page keeps the endpoint inside the latency budget.
- **Alternatives considered**: one row per receipt line (the total would count lines, not receipts, and the same `GR-` number would appear many times — rejected); storing an aggregate column on `goods_receipts` (a stored sum of quantities with different units is meaningless, and it would need recomputation on every write — rejected); returning the lines and letting the browser sum them (the browser would have to know the unit rule, and the count would drift from the server's — rejected); a separate endpoint for the line-level view (a second contract for a case the specification did not ask for — rejected).

## D13 — The purchase-order list carries a server-computed progress summary

- **Decision**: Each order row carries a progress summary the server computes with exact decimals: when every line of the order shares one unit of measure, the received total, the ordered total and the unit abbreviation; otherwise the number of fully received lines and the line count, where a line counts as fully received when `quantity_received = quantity_ordered`. The summary is derived from the quantities actually received, not from the status: a `DRAFT` carries no progress figure, a `CANCELLED` order carries the progress it reached, a `RECEIVED` order carries complete progress. The progress column is neither sortable nor filterable. The order detail always shows the per-line table of ordered, received and outstanding quantities, so the list figure is a summary only.
- **Rationale**: The same mixed-unit problem the receipts list solved applies here, and the same rule answers it: a quantity aggregate is shown only when it means something, otherwise the line counts are. Computing it on the server keeps one rule in one place — the browser never re-derives a figure the server already knows — and the status/progress consistency is then provable by one test over a seeded set of orders.
- **Alternatives considered**: always showing the aggregate (meaningless across units — rejected); always showing "N of M lines" (loses the quantity information in the common single-unit case — rejected); letting the client compute it from the order's lines (the list would have to carry every line of every order, and two implementations of one rule — rejected); sorting by progress (a quantity has no total order across units — rejected).

## D14 — The unit of measure is captured on the document lines

- **Decision**: `purchase_order_lines` stores the product's unit-of-measure **abbreviation** (`varchar(16)`) when the line is entered, and `goods_receipt_lines` copies it from the order line. The abbreviation is a snapshot, not a foreign key: it is text, it is taken from the product's unit through the owning Products service, and it never changes when the product's unit is edited later.
- **Rationale**: D12 and D13 compare units to decide whether an aggregate is meaningful, and the receipt history must keep showing the unit the goods actually arrived in. A live join to `products.unit_id` would let a later product edit rewrite the history of a posted receipt — the same reason the constitution copies prices onto document lines. The snapshot is the only way both the aggregate rule and the permanence of a receipt can hold.
- **Alternatives considered**: joining the product's unit at read time (a later product edit changes a posted receipt's history — rejected); storing the unit id as a foreign key (still follows the product — rejected); a per-receipt unit field (a receipt can hold lines of different units, so there is no single value — rejected); no unit on the lines at all (the aggregate rule has nothing to compare — rejected).

## D15 — One shared module gate, and the refusal that is deferred

- **Decision**: Every purchasing endpoint declares **one** shared gate — a NestJS guard named for the module (`PurchasingModuleGuard`), applied to the purchasing controllers and reading a guard metadata key. Today the guard allows every request; its body is the single place where the settings feature will enable the module-disabled check, so no endpoint has to change when it arrives. No `organization_modules` table, no toggle endpoint and no interface for one are added by this feature. The canonical Purchasing documentation records the deferred requirement and names the Organization settings feature (P0-F002) as its owner, with the rules it must apply to Purchasing: Purchasing requires Inventory, and turning Purchasing off is refused while any order is `DRAFT`, `CONFIRMED` or `PARTIALLY_RECEIVED`. A test enumerates the purchasing controllers and their handlers and asserts that each declares both its permission and the gate. The interface keeps showing Purchasing as available in the sidebar and never simulates a "turned off in Settings" state.
- **Rationale**: The constitution requires module availability to be enforced server-side, and the PRD assigns that capability to P0-F002, which does not exist yet. Shipping the gate now means the rule has exactly one home when it arrives, and shipping the table here would duplicate another feature's scope (and the specification forbids it). The declaration test closes a real gap: the existing default-deny test proves the guard's behaviour with synthetic probe controllers and does **not** enumerate the application's endpoints, so the purchasing endpoints would otherwise have no proof that they declare anything.
- **Alternatives considered**: implementing the table and the toggle here (duplicates P0-F002, adds a settings screen the specification forbids — rejected); `forwardRef` to break the module cycle (the constitution prohibits circular module dependencies — rejected); a global event bus (new infrastructure and eventual consistency for a synchronous check — rejected); skipping the gate until the settings feature exists (the check would then have to be added endpoint by endpoint, which is the cost the gate is meant to avoid — rejected).

## D16 — The document sequences are provisioned on first use, with constraints

- **Decision**: The `PO-` and `GR-` sequence rows are created on first use, inside the transaction that creates the document, under `pg_advisory_xact_lock(hashtext('<organizationId>:<name>'))` — the Inventory adjustment pattern — so two concurrent first-uses cannot allocate the same number or create two rows. The migration adds a unique constraint on `document_sequences ("organizationId", name)` — the table's grandfathered camelCase columns — and the two document tables keep their unique indexes on `(organization_id, number)`. The numbers keep the six-digit format the specification states, while the contacts and adjustment sequences use five.
- **Rationale**: Existing organizations have no purchasing sequence rows, and a backfill would write rows for every organization that may never order. The advisory lock is already the proven allocation pattern in this codebase, and the unique constraint turns any missed race into a constraint violation the transaction rolls back rather than a duplicate row. The six-digit format is the specification's own, and the width difference with the older sequences is recorded as a separate consistency decision rather than silently changed here.
- **Alternatives considered**: backfilling every organization in the migration (writes rows nobody asked for, and the allocation still needs a lock — rejected); the Contacts find-then-create upsert without a lock (two simultaneous first-uses can both create a row — rejected); PostgreSQL `SEQUENCE` objects (a new mechanism, and gaps are harder to reason about per organization — rejected); counting existing rows (races, and reuses numbers after a delete — rejected).

## D17 — The receive dialog starts blank, offers one bulk action, and confirms before posting

- **Decision**: The dialog opens with every quantity field **blank** — no per-line prefill and no `0.000` default — and offers one "Receive all outstanding" action that fills only the lines that still have an outstanding quantity; every field stays editable and clearable, and a line with no outstanding quantity shows its field disabled and marked "Fully received". The post action stays disabled until at least one line carries a quantity above zero, and a blank quantity and a zero quantity both mean "not received on this line". Before posting, a confirmation summary names the lines and quantities, the resulting order status, and the consequence that the receipt increases stock and cannot be edited or deleted. Quantities are entered and held as decimal strings with at most three decimals and never pass through a floating-point value; a quantity above the line's outstanding quantity shows an inline error naming that outstanding quantity. The idempotency key is generated when the dialog opens and reused on every retry; a new key is generated only when the previous attempt ended in a definite answer (a success or a definite failure), so an attempt whose outcome was unknown keeps its key and a double click posts one receipt. After a successful post the dialog closes, a toast names the `GR-` number, and the order's received and outstanding figures refresh.
- **Rationale**: Blank fields keep an accidental full receipt impossible while one bulk action keeps the common case one click away. A confirmation step is the PRD 7.3 requirement for an irreversible action, and stating the consequence is what makes the confirmation meaningful. The key rule is the one that prevents a duplicate receipt: a network timeout leaves the outcome unknown, and reusing the key turns the retry into a replay of the stored answer instead of a second receipt.
- **Alternatives considered**: prefilling every field with the outstanding quantity (one click posts everything, including the goods that did not arrive — rejected); prefilling `0.000` (noise, and a zero is not a receipt — rejected); no bulk action (the common case becomes twenty keystrokes — rejected); generating a new key on every reopen (a retry after a timeout would post twice — rejected); keeping the key forever (a later, unrelated receipt would replay the first answer — rejected).

## D18 — Who may post a receipt

- **Decision**: Posting a receipt keeps the `inventory.receive` permission, so the shipped role templates need no change: the `purchasing` template grants `purchasing.read` and `purchasing.write` (create, update, confirm, cancel) and **not** `inventory.receive`; the `inventory` template already grants `inventory.receive` and `purchasing.read`, so the clerk who receives goods can see the order it receives against. The two personas in the specification — the purchasing officer who prepares orders and the inventory clerk who receives them — map exactly onto the two templates.
- **Rationale**: The specification assigns the receipt to the clerk and the order to the officer, and both permission codes already exist in the shared catalogue, so no catalogue change and no seed change is needed. The receiving clerk can read the order because the goods-receipts list and the order detail both use `purchasing.read`, which the `inventory` template already carries.
- **Alternatives considered**: granting `inventory.receive` to the `purchasing` template as well (one role could then both order and receive, which blurs the separation the specification's two personas describe — rejected); a new `purchasing.receive` permission (the catalogue already names `inventory.receive` for exactly this action, and a second code would split one action across two catalogues — rejected).
