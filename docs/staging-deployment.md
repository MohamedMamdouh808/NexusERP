# Staging Deployment Runbook

**This environment is staging.** It exists so that a reviewer can open one HTTPS address and see the
product working against a real database. It is **not** production: it runs on entry plans, it has no
availability target, no support commitment, and no backup guarantee beyond whatever the providers
give by default. Nothing here should be read as a production readiness statement.

This is the single document that takes a reader from empty provider accounts to a serving staging
address, and from a bad deploy back to a good one.

---

## 0. What staging is made of

| Component | Host | What the repository contributes |
|---|---|---|
| Interface (React shell) | Vercel | [`frontend/vercel.json`](../frontend/vercel.json) — the `/api` rewrite and the single-page fallback |
| Service (NestJS API) | Render | [`render.yaml`](../render.yaml) — one native Node web service |
| Database | Supabase | Nothing; it is a managed project, not a built component |

The browser talks to **one origin**, the interface's own Vercel domain. That domain forwards
`/api/*` to the Render service, so the interface's API calls are same-origin and no cross-origin
policy is exercised at runtime. There is no custom domain anywhere in this environment; the
forwarding rule, not a DNS record, is what makes the single origin real.

The service runs on Render's **native Node runtime**. There is no container image: Render runs the
repository's own build and start commands, which are the same commands the local gate set runs, so
the deployed artefact and the tested one cannot drift.

## 1. Create the projects

Create these three, in this order. Nothing about the setup can be expressed in the repository:
provider accounts, the Git integration, and the branch protection below are all set up once by a
human with account access.

| # | Project | Plan to select | Notes |
|---|---|---|---|
| 1 | Supabase project, PostgreSQL **17** | Free | Pick the PostgreSQL **17** major version explicitly. The rest of the project is pinned to 17, and a migration verified against 17 must not fail only because staging runs something else. |
| 2 | Render Blueprint from this repository | Free web service | Render reads [`render.yaml`](../render.yaml) and creates the service. `DATABASE_URL` is left for you to enter once (§2). |
| 3 | Vercel project for the frontend | Hobby | **Root Directory** must be set to the frontend workspace, and **"Include source files outside of the Root Directory in the Build Step"** must be **enabled** — the frontend builds against the `shared` workspace, which lives above the Root Directory. |

**Two settings that are easy to miss and silently inert when missed:**

- A `vercel.json` is honoured only when it sits in the project's **Root Directory**. The file is
  committed at `frontend/vercel.json` for exactly that reason; moving it to the repository root
  would make it inert, and the deployment would then serve the interface with no `/api` route.
- A Render Blueprint defaults to `render.yaml` **at the repository root**. That is why it lives
  there rather than under a `deploy/` directory.

Staging must share nothing with development or test: its own database, its own configuration, its
own secrets. Do not point it at a local PostgreSQL instance, and do not reuse a development secret.

## 2. Configure

Every variable the service consumes, the platform that sets it, and what it controls. Secrets are
marked; **no secret value appears in this document, in the repository, or in a deploy definition**
(FR-027, FR-028).

### On Render — the service

| Variable | Set it to | Secret |
|---|---|---|
| `NODE_ENV` | `production` | no |
| `LOG_LEVEL` | `info` | no |
| `CORS_ORIGINS` | the interface's own origin — `https://<your-vercel-domain>` | no |
| `TRUST_PROXY` | `1` — the number of proxies actually in front of the service | no |
| `DATABASE_URL` | entered once in the Render Dashboard (`sync: false`) | **yes** |
| `SESSION_SECRET` | generated by Render (`generateValue: true`) | **yes** |
| `CSRF_SECRET` | generated by Render (`generateValue: true`) | **yes** |

All but `DATABASE_URL` are declared in the Blueprint and are set for you. `DATABASE_URL` is the one
value a human enters, because it embeds a credential and cannot be generated.

**The connection string.** In Supabase, open **Connect** and take the **session pooler** address —
not the direct connection, and not the transaction-mode pooler. The session pooler is used for both
application traffic and migrations, so one URL covers both. The transaction-mode pooler is not used
because it does not keep the session that a schema change needs.

**`CORS_ORIGINS` is an explicit allowlist.** The environment schema rejects `*`, because a wildcard
origin combined with credentials lets any site issue authenticated requests as the signed-in user.
With the rewrite in place the browser is same-origin and this list is not exercised, but it stays
required and non-wildcard.

**`PORT` is deliberately not set.** The platform supplies it, and declaring it in the Blueprint would
override the platform's value with a fixed one. The service binds `0.0.0.0` on whatever port the
platform provides.

**`TRUST_PROXY`.** Off by default everywhere. In staging it is set to the **number of hops actually
in front of the service**, never to a blanket `true`: a hop count higher than reality means the
service trusts a forwarding header a caller can supply, which is exactly the spoofing path the
off-by-default setting closes. The recorded client address is what later rate limiting and audit
work will rely on.

### On Vercel — the interface

| Variable | Value |
|---|---|
| *(none)* | The interface consumes **no** runtime environment variable. It calls the API through relative paths under `/api`; the service's hostname lives in the `vercel.json` rewrite target, and nowhere in the interface's configuration. |

`VITE_API_PROXY_TARGET` is **not** set here. It is a development and preview concern only, used by
`vite.config.ts` to point the dev and preview servers' `/api` proxy at a running service.

### On Supabase — the database

| Setting | Value |
|---|---|
| PostgreSQL major version | **17** |
| Data API (the provider's automatic REST surface) | **Disabled** |
| Connection address used by the service | the **session-mode pooler** |

Disabling the Data API is part of the setup, not an optional hardening step — see §4 for the check
that proves it, and the appendix for what it is holding shut.

## 3. First deploy

1. **Merge to `main`.** Each host deploys from the repository through its own Git integration when
   `main` changes. A merge to `main` is the only trigger; Render is configured to deploy **only
   after the mandatory checks pass** for the exact commit being deployed, so a commit whose checks
   are still running is never deployed.
2. **Migrations run as part of bringing the version up.** The service's start command applies the
   repository's pending migrations **before** the service begins listening, and the platform's
   health check is not answered until they have finished. There is no second migration route: the
   free plan provides no pre-deploy step, so the start command is the one route (FR-015).
   The first deploy therefore applies the **full migration history to an empty database**.
3. **The service must pass its health check** at `/api/v1/health` before it receives traffic. A
   version that fails the check is discarded rather than left partially live.
4. **Re-running a deploy that already succeeded changes no data and applies no migration twice.**
   Migrations are recorded as applied, and reference data is upserted rather than duplicated.

### No manual step after the checks pass

Once the mandatory checks are green on a merge to `main`, updating staging requires no human action.
A deploy that needs a human is a deploy that gets skipped.

### The failing-migration rehearsal (do this once, and record it)

Staging has to demonstrably survive a bad migration, not merely claim it would. Deliberately add a
migration that fails, merge it, and observe:

| What to observe | Expected |
|---|---|
| The deploy | Aborted; the version that was serving before keeps serving the staging address once the attempt ends |
| The database | Left at its last successfully applied state: no partially applied change, and the failed migration **not** recorded as applied |
| The deploy history | The failed attempt appears and is discarded, not left partially live |

**Record what was actually seen, including any interruption.** The requirement is that the previous
version is what serves when the attempt ends — **not** that the replacement is interrupt-free. Entry
plans do not promise continuity, and this runbook does not claim it: write down the interruption you
observed, if any, rather than a smoother story.

Then apply the recovery: roll forward with a corrected migration (§5) rather than editing the
database by hand.

## 4. Verify

Work through these once, after the first deploy. Each one is checkable from outside the system.

| # | Check | How | Passes when |
|---|---|---|---|
| 1 | The interface renders | Open the staging address over HTTPS | The application shell loads: sidebar, top bar with organization switcher and user menu, content area, and a health panel |
| 2 | Health through the staging address | `curl https://<your-vercel-domain>/api/v1/health` | A success response, with the application check and the database check reported **separately**, and the database check `ok`. This also proves the `/api` rewrite reaches the service and that the rewrite precedes the single-page fallback |
| 3 | The response is same-origin | Open the browser's network panel on the staging address | Zero blocked or cross-origin requests caused by the interface's API calls |
| 4 | Database major version | `SELECT version();` in the Supabase SQL editor, or the project's settings page | PostgreSQL **17** |
| 5 | The data surface is closed | `sh scripts/check-supabase-data-api.sh` with `SUPABASE_PROJECT_REF` and `SUPABASE_ACCESS_TOKEN` set | **Both** assertions hold: an anonymous request naming a known table at the project's own REST surface is refused and discloses no rows, **and** the project reports its Data API **disabled** |
| 6 | Branch protection actually blocks | See §6 | A pull request carrying a deliberately failing check cannot be merged |
| 7 | No secret in the repository | `node scripts/check-secrets.mjs` | Zero findings, and the deploy definitions contain no secret value |

Check 5 has **two** assertions on purpose. A mistyped address, a missing project, or an unrelated
error would all produce "no rows", so the refusal alone could pass for the wrong reason; the second
assertion is what makes the result non-vacuous.

## 5. Roll back

**Procedure.** In Render, open the service's **deploy history** and roll back to the previously
successful deploy. That restores the previous version. No manual database edit is part of this
procedure, and none may become part of it.

**What a rollback restores.** The application version only.

**What a rollback cannot undo — a schema change.** Migrations here are forward-only; there are no
down migrations. So a rollback after a migration has been applied returns the *code* to the earlier
version while the database stays at the newer schema. That is why schema changes on staging must be
**additive and backward-compatible** with the version one deploy behind: add a nullable column, add
an index, backfill in a later step. A destructive change (dropping or retyping a column) removes the
option of rolling back at all, because the version being restored would then be reading a schema
that no longer exists.

**Preferred recovery from a bad migration.** Correct forward: revert the offending migration's
effect in a new migration and deploy again. Use the rollback button for a bad *application* version.

## 6. Protect `main`

Branch protection is a **required part** of this setup, not optional configuration. It is what makes
"a deploy runs only after the checks pass" true: the hosts deploy on push, so the commits they can
see must only ever be commits that already passed.

Configure, on `main`:

1. **Every mandatory check is a required status check.** Every job in
   [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) — Lint, Type check, Unit tests,
   Integration tests (real PostgreSQL), Migration validation, Contract drift, Build, Secret scan,
   and Workflow assertions. A job that is not required is a job that can fail while the merge
   proceeds.
2. **The branch must be up to date before merging**, so a merge is tested against the tip it lands
   on.
3. **No direct pushes.** Changes reach `main` through a pull request only.

### Verify it, do not assume it

An unverified protection setting is indistinguishable from an absent one. So demonstrate the
refusal **once** and record it here:

| Step | Expected |
|---|---|
| Open a throwaway pull request that contains a deliberately failing mandatory check | The merge is blocked, and the blocking check is named |
| Attempt to push directly to `main` | Rejected |
| Close the pull request without merging | The branch is unchanged |

> **Recorded result:** _pending — to be filled in when staging is set up, with the pull request
> number, the date, and the check that blocked it._

A pipeline that deploys is not how this is achieved: the pipeline's terminal action stays
verification, and no workflow step deploys, publishes, restarts, or releases anything in a hosted
environment.

**Frontend preview deployments.** Pull-request previews may be produced. A preview must not read,
write, or migrate the staging database — it is a build of the interface, and nothing in the
interface reaches the database except through the service it is pointed at.

## 8. Backup

Stated as plainly as possible, because a backup claim that overstates is worse than none:

| Component | What the provider gives | What it does **not** give |
|---|---|---|
| Interface (Vercel) | Nothing to back up: it holds no state. Any previous deployment is rebuildable from the repository | Point-in-time data recovery, because there is no data |
| Service (Render) | Nothing to back up: it holds no state | Persistence of any kind |
| Database (Supabase) | Whatever the selected plan's own automatic backups retain — **and no more** | Any retention this project configures; this repository takes **no** dumps, keeps **no** snapshot of its own, and schedules **no** export. A restore is not tested here, so restoration is not demonstrated either |

So the **only** state in staging is the database, and the **only** protection over it is whatever the
provider's plan includes. Nothing in this repository adds to it.

> **Recorded retention:** _pending — read the retention the Supabase dashboard reports for this
> project's plan, and write the figure here when staging is set up._

### The retention gap is an open product-requirements decision

The difference between what the providers retain and what the product will eventually need is **not
resolved here**. It is recorded as open in the product requirements, deliberately: resolving it
means choosing a retention period and a restore objective, which is a product decision with a cost,
not a side effect of standing up a staging environment.

Nothing in this runbook, and nothing in the staging environment, promises a recovery point
objective, a recovery time objective, or an availability figure. Those claims attach only when they
are real.

## 9. Entry-plan behaviour you will observe

These are known behaviours of the plans in §7. They are **not defects**, they are not incidents, and
they are not worked around by buying an upgrade.

| What you may see | Why | What to do |
|---|---|---|
| The first request after a quiet period is slow | The free service instance stops when idle, and the next request pays a cold start | Wait. It warms on the first request |
| A health request fails after a long quiet period, then succeeds on retry | The database project pauses when idle and takes a moment to wake | Retry. If it stays down, check the service's logs before changing anything |
| A deploy takes a while to appear | Free instances are single, low-spec, and restart rather than overlap | Wait for the platform's deploy history to report completion |
| The deploy history does not go back indefinitely | The free plan keeps a limited number of deploys | Treat the repository as the source of truth: any commit can be redeployed |
| There is **no pre-deploy step** | The free plan does not provide one | This is why migrations run in the start command (§3). Do not add a second migration route to compensate |
| A failed deploy is not interrupt-free | The requirement is that the previous version serves **after** the attempt ends — not that the replacement is seamless | Record what you observed in §3 rather than claiming continuity |

## 10. Out of scope

Named explicitly so that no reader infers more than this environment delivers:

- **A production environment.** Staging is staging: entry plans, no availability target, no support
  commitment, no production data, and no production secrets.
- **A custom domain.** The single origin comes from the interface host's own forwarding rule over
  its default domain. No DNS record, no certificate, and no subdomain pointed at the service.
- **Paid plan upgrades.** None was purchased; see §7.
- **Backups beyond what the providers give.** No dumps, no snapshots, no scheduled exports, no
  tested restore; see §8.
- **A monitoring vendor.** Nothing is selected. Each platform's own logs and deploy history are what
  exists, and they are not aggregated, alerted on, or retained beyond what the platform keeps.
- **Authentication.** The staging service serves exactly one unauthenticated route, the health
  address. Sign-in, sessions, permissions, and tenant scoping arrive with later features; the
  `SESSION_SECRET` and `CSRF_SECRET` values exist on staging only so that a later feature does not
  have to add a secret to a running environment.
- **A staging data model of its own.** Staging runs the same migrations as every other environment.
  A change that only exists on staging is a change nobody can reproduce.

### Seed content loaded into staging

Staging receives the repository's reference data and **nothing else**: the permission catalog and
the role templates, upserted by `npm run db:seed`. These are application definitions — permission
codes and role templates — **not records**. No organization, no user, no business document, and no
transaction is loaded, so nothing in staging's database should be mistaken for real data.

## Appendix: what the data surface is holding shut

The provider offers an automatic REST surface over the project's database, reachable over HTTPS with
the project's public key and no application involvement. It is **disabled** (§2), and §4 check 5
proves it. If it were enabled, the following would become reachable **without passing through the
service at all**:

- every table in the database's exposed schema, addressed by name;
- for each of them, whatever the database's own row-level security permits — and since the
  application's permission checks live in the *service*, not in the database, the service's
  authorization is not in that path;
- with it, the tenant scoping the service applies per request, which the provider's surface has no
  concept of.

Re-enabling it is therefore a deliberate decision with a security consequence, not a toggle to flip
to make a query convenient. If it is ever enabled, that decision belongs in a review, not in a
dashboard click.
